    src/tx.py — the whole mechanism

      Lines 5–10 are what a DAO actually holds. current_session() hands back this wrapper, not the AsyncSession, so everything a DAO needs passes through but commit, rollback, close and begin raise. One await current_session().commit() inside the boundary would otherwise split it, and the half that ran before the call would survive the rollback of the half that ran after it.

      Lines 15–18 keep the session on the task that opened it. A ContextVar is copied into every task spawned inside the boundary, so an asyncio.gather() of service calls would otherwise drive one AsyncSession from several tasks at once. The lookup refuses instead.

      Line 26 is the propagation rule. A context already set means a transaction is open, so the call joins it and the decorator gets out of the way. This is Spring's REQUIRED.

      Lines 29–32 are participation semantics. A joined call that fails marks the whole transaction rollback-only, so a caller cannot swallow the failure and commit half the work. The catch is BaseException because asyncio.CancelledError is not an Exception: a joined call killed by asyncio.timeout() has to poison the transaction too, or a swallowed TimeoutError commits half a transfer.

      Line 39 is the boundary. session.begin() commits when the method returns and rolls back when it raises, so business logic is never wrapped in a swallowing except.

      Lines 42–47 refuse the commit when a joined call already failed, the same way Spring throws UnexpectedRollbackException. Line 43 compares identities so that a failure simply propagating out of the boundary reaches the caller unchanged instead of being masked, and the exception that poisoned the transaction, not whatever the caller tripped over afterwards, becomes the __cause__ of the rollback.

      Lines 48–50 are the last thing between a return and a commit. Rollback-only only fires when the failure crossed a @transactional frame; a database error caught straight off a DAO does not, and Postgres has already killed that transaction. Committing a dead transaction is a silent no-op, so without this check the boundary would return success for work the database threw away.

      Line 53 restores the previous context in a finally, so a rolled-back call leaves nothing behind for the next call on the same task.

      src/service.py — one boundary, four participants

        Line 6 locks both rows, line 7 calls LedgerService, a different service with its own @transactional methods, and lines 8–9 call back into this same service. Every one of them runs inside the one transaction that line 1 opened, and the DAOs underneath find it through current_session(). The lock comes before the ledger row because it is what proves both accounts exist: a missing account has to fail as AccountNotFound and a 404, not as a foreign key violation.

        Contention — the boundary is not enough on its own

          A correct transaction still loses updates if the balance is read, changed in Python and written back: two concurrent deposits both read the same number and one overwrites the other. Ten concurrent deposits of 10.00 into an empty account produced 20.00 instead of 100.00 before this lock existed.

          SELECT ... FOR UPDATE makes the read block until any other transaction holding that row commits, so the read-modify-write becomes serial per account. ORDER BY id is the other half: Postgres puts its LockRows node above the Sort, so both rows are locked in ascending id order and alice → bob and bob → alice running at the same time cannot each hold the row the other one wants. Inserting a ledger row takes a foreign key lock on each account it names, in column order rather than ascending, so record() takes the same ascending lock first and no two writers ever queue in opposite orders.

          Nothing retries, on purpose. An aborted transaction cannot be resumed, only re-run from the top, so a retry loop inside @transactional would silently re-execute the whole business method including whatever it did that Postgres cannot roll back. Retry belongs around the service call, where the caller knows whether running it twice is safe, and it belongs there with an explicit list of what it catches: 40001 and 40P01 are worth another attempt, InsufficientFunds and a CHECK violation are the same answer every time. At READ COMMITTED with the lock order above, this design produces neither, so the loop would be dead code today.

          The database is the backstop, not the referee. CHECK (balance >= 0) and the foreign keys from ledger to accounts mean a bug in the service cannot leave a negative balance or an orphan row behind, and lock_timeout means a stalled transaction cannot hold a hot account forever.

          Money itself is checked before any of this. Numeric(18, 2) rounds on write, and a transfer rounds its debit and its credit separately, so moving 0.125 takes 0.12 from one account and gives 0.13 to the other. Twenty of those mint a cent each and CHECK (balance >= 0) never notices, because what breaks is conservation, not sign. An amount finer than a cent is refused.

          Both claims are automated in tests/test_contention.py, which fails on three tests when the lock is removed and on a fourth when record() stops taking the lock.
