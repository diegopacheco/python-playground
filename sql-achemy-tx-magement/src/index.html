    src/tx.py — the whole mechanism

      Lines 1–13 keep the session on the task that opened it. A ContextVar is copied into every task spawned inside the boundary, so an asyncio.gather() of service calls would otherwise drive one AsyncSession from several tasks at once. A worker thread from asyncio.to_thread() gets the copy too and has no running loop, which is why the task lookup answers "no task" instead of raising about the event loop.

      Lines 33–49 wrap the context managers the session hands out, which is the one route a block list of names cannot see because the leak is not the name, it is what the object carries. no_autoflush is a @contextmanager, and a @contextmanager yields the sync Session and keeps it in gi_frame.f_locals as well — so the name that stays allowed was a sixth way to reach the object run_sync, sync_session, _proxied, object_session and _proxy_objects are all refused for, and greenlet_spawn(session.commit) through it is exactly what run_sync would have done. Refusing the name would break a session API the wrapper is supposed to pass through, so entering and exiting cross and nothing else does: line 42 gives the boundary wrapper back rather than the session the manager yielded, and line 49 refuses every other name on the way in.

      Lines 57–62 are the two refusals every route into the session shares. The first is the wrapper going dead with its boundary: an AsyncSession autobegins on next use, so a session kept past the call that opened it would quietly start a second transaction that nothing can ever commit and never hand its connection back to the pool. The second is the task check, which current_session() alone was not enough for: capture the wrapper inside the boundary, hand the object to a spawned task, and that task drove the session anyway while the boundary committed its writes.

      Line 115 and lines 126 and 133 are why one check is not three. Guarding only the lookup guards the object and not the use, and what travels into another task does not have to be the wrapper: a bound method taken off it inside the boundary carried no check at all, so execute = current_session().execute handed to a spawned task put the ghost row back and the boundary committed it. Re-checking inside the callable closes the captured method, the captured method used after the boundary returned, and gather(session.execute(...), session.execute(...)) — where the lookup happens on the right task and only the await moves — with the one check the lookup could never make.

      Lines 65–68 are the block list, and every route into the session runs it: the lookup on line 116 and the assignment on line 106 share this one method. current_session() hands back this wrapper, not the AsyncSession, so everything a DAO needs passes through but commit, rollback, close, aclose, begin, connection, get_bind, bind, get_transaction, get_nested_transaction, identity_map, sync_session, run_sync, _proxied, _proxy_objects and object_session raise. One await current_session().commit() inside the boundary would otherwise split it, and the half that ran before the call would survive the rollback of the half that ran after it. sync_session, run_sync, _proxied, object_session and _proxy_objects are five names for the same sync Session, so blocking four of them blocked nothing. bind is the one that shows what a list costs: it is the same engine get_bind is refused for, assigned on the instance rather than declared on the class, so it never appears in dir(AsyncSession) and the audit that wrote the list did not see it. A write through it ran on its own connection, committed itself, and survived the rollback the boundary performed around it. It is a guard against a mistake and not a sandbox, and the list can only name what lives on the session: _session is still an attribute, and result.connection is not a session name at all, which is what lines 207–217 answer for. What an allowed name carries is not a session name either, which is what lines 33–49 answer for.

      Lines 69–74 refuse stream() and stream_scalars(), which are the one hole in the recorder below. A server-side cursor raises while the result is iterated, not inside the session call the boundary wrapped, so a swallowed failure there left the transaction poisoned with nothing recording it and the boundary returned success for work Postgres had thrown away. Guarding the result object would mean proxying every way of reading it; refusing the two methods costs a POC that does not stream nothing. execute() asked for the same cursor with stream_results or yield_per is closed by SQLAlchemy itself, which shuts the cursor and raises before a row is read, so the transaction survives that route rather than escaping through it.

      Lines 87–91 refuse the session's own context manager. async with session: closes it on the way out, which is close() reached through a syntax no block list can see: Python looks __aenter__ up on the type, so the name check on line 116 never runs. It used to be a TypeError about a missing __aexit__, which is a refusal by accident rather than an answer the caller can act on.

      Lines 93–99 are the two session APIs a wrapper made of __getattr__ loses. entity in session and list(session) are resolved on the type, so they never reached the lookup and never reached the session either: both were a TypeError naming BoundarySession. That is the wrapper breaking a session API instead of passing it through or refusing it by name, which is the one thing this design is not allowed to do, and it is the same blind spot lines 87–91 cover from the other side.

      Lines 101–107 guard the assignment, which is the route a block list on the lookup alone can never close. current_session().autoflush = False used to set the attribute on the wrapper and never reach the session, and because an instance attribute shadows __getattr__, reading it back returned the value that had not been applied: the wrapper reported the setting while the session went on flushing. That is exactly the silent change of meaning line 118 exists to prevent. The sharper half is that the assignment could switch the block list off — current_session().bind = ... shadowed the refusal, so the next read handed back the assigned value instead of raising. Assignment now takes the same guard and the same block list the lookup does, and lands on the real session.

      Lines 109–112 guard the deletion, which is the third route into an attribute and the one that was left open when the read and the assignment were closed. It reached nothing on the session, so a del the caller believed had landed had not; and because the two names the wrapper keeps for itself live in its own __dict__, deleting one of those left the lookup on line 114 recursing into itself until Python gave up. A RecursionError names nothing, and every other route the wrapper will not allow says what it is.

      Lines 118–129 wrap the methods that are not coroutines. add() and expunge() stage work without any await, so they used to be handed back untouched and were the one route with no guard on it in any form: a worker thread staged an entity through a captured add and the boundary flushed and committed the row. Line 118 asks for a routine and not for anything callable, which is the difference between guarding a session API and breaking one. A @contextmanager object is callable, because a context manager doubles as a decorator, so no_autoflush came back wrapped in a plain function with no __enter__ and with current_session().no_autoflush: was a TypeError. Everything the wrapper will not allow says so and names itself; silently changing what a call means is the one thing it must never do.

      Lines 131–141 are why a swallowed database error cannot be committed over. Every await a DAO makes goes through here, so a DBAPIError or a cancelled statement is recorded as the failure that poisoned the context before the caller ever gets the chance to catch it. It has to happen here rather than at the commit: SQLAlchemy deactivates its SessionTransaction on a failed flush only, so after a failed execute() it still reports is_active true while psycopg reports the connection INERROR, and the COMMIT that follows is a silent no-op. Line 135 is the bookkeeping, and it runs on the way in rather than on the way out: lines 76–85 check the connection out, mark the transaction and record the identity the checks at the end compare against. A recorder that armed itself after the call could only arm on a call that left Postgres inside a transaction, so a raw COMMIT as the first statement armed nothing at all and the next call armed the nets on the transaction that had replaced the boundary's. A method that never touches the session still costs nothing, because nothing opens.

      Lines 177–178 refuse a function that is not async def at import time. The wrapper awaits what it wraps, so without this the mistake surfaced at call time as a TypeError about the return value rather than at the decorator that is wrong.

      Line 183 is the propagation rule. A context already set means a transaction is open, so the call joins it and the decorator gets out of the way. This is Spring's REQUIRED.

      Lines 186–189 are participation semantics. A joined call that fails marks the whole transaction rollback-only, so a caller cannot swallow the failure and commit half the work. The catch is BaseException because asyncio.CancelledError is not an Exception: a joined call killed by asyncio.timeout() has to poison the transaction too, or a swallowed TimeoutError commits half a transfer.

      Line 195 is the boundary. session.begin() commits when the method returns and rolls back when it raises, so business logic is never wrapped in a swallowing except.

      Lines 198–203 refuse the commit when a joined call already failed, the same way Spring throws UnexpectedRollbackException. Line 199 compares identities so that a failure simply propagating out of the boundary reaches the caller unchanged instead of being masked, and the exception that poisoned the transaction, not whatever the caller tripped over afterwards, becomes the __cause__ of the rollback.

      Lines 204–206 are the second net behind lines 131–141. Committing a transaction Postgres already killed is a silent no-op, so without a check the boundary would return success for work the database threw away. This one catches a transaction that ended some other way than a statement error.

      Lines 207–212 are the third net, and the only one that asks the connection rather than the session. The Result that execute() hands back carries the very Connection the boundary is holding, and result.connection is not a session name, so no block list can reach it. A commit through it split a transfer: the debit committed and the boundary rolled back the credit around it. SQLAlchemy's SessionTransaction still reports is_active true afterwards, so lines 204–206 see nothing — but the connection knows, and in_transaction() is false. Asking only that much was not enough: any session call made after the split autobegins a fresh transaction on the same connection, so in_transaction() answered true again and the boundary went back to failing at COMMIT with the raw InvalidRequestError this net exists to replace. Line 211 asks for the transaction the boundary started rather than for any transaction at all, and line 83 is where that one was captured, on the way into the first session call. A raw ROLLBACK string gets past all three of these, because it ends the transaction inside Postgres where neither the session nor the connection is told, which is what the net below answers for.

      Lines 213–217 are the last two nets, and the only ones that ask the driver. Everything above them asks SQLAlchemy, and SQLAlchemy is exactly what a raw COMMIT or ROLLBACK string goes around: the string ends the transaction inside Postgres, the session and the connection are never told, the transaction object is still the one line 83 recorded, and the boundary reported success over work the database had thrown away. Line 214 asks libpq, which tracks the transaction status of the socket with no round trip, and that answers for a transaction that ended or was aborted and left the socket idle — including a commit made straight on psycopg's connection through result.connection.connection.dbapi_connection. A status is not an identity, though: one string can end the boundary's transaction and open another in its place, and the socket reads INTRANS again before anything looks. So line 82 marks the transaction on the way in with a SET LOCAL that Postgres throws away when that transaction ends — and, because application_name is reported, tells the client it did. Line 216 reads the mark back off the socket, locally, and a mark that is gone means the transaction that carried it is gone too. What stays open is a write on a second connection: it commits itself on a socket the boundary never held, so there is nothing here to ask.

      Lines 219–221 close the context and restore the previous one in a finally, so a rolled-back call leaves nothing behind for the next call on the same task.

      src/service.py — one boundary, four participants

        Line 4 locks both rows, line 5 calls LedgerService, a different service with its own @transactional methods, and lines 6–7 call back into this same service. Every one of them runs inside the one transaction that line 1 opened, and the DAOs underneath find it through current_session(). The lock comes before the ledger row because it is what proves both accounts exist: a missing account has to fail as AccountNotFound and a 404, not as a foreign key violation.

        Contention — the boundary is not enough on its own

          A correct transaction still loses updates if the balance is read, changed in Python and written back: two concurrent deposits both read the same number and one overwrites the other. Ten concurrent deposits of 10.00 into an empty account produced 20.00 instead of 100.00 before this lock existed.

          SELECT ... FOR UPDATE makes the read block until any other transaction holding that row commits, so the read-modify-write becomes serial per account. ORDER BY id is the other half: Postgres puts its LockRows node above the Sort, so both rows are locked in ascending id order and alice → bob and bob → alice running at the same time cannot each hold the row the other one wants. Inserting a ledger row takes a foreign key lock on each account it names, in column order rather than ascending, so record() takes the same ascending lock first and no two writers ever queue in opposite orders.

          Nothing retries, on purpose. An aborted transaction cannot be resumed, only re-run from the top, so a retry loop inside @transactional would silently re-execute the whole business method including whatever it did that Postgres cannot roll back. Retry belongs around the service call, where the caller knows whether running it twice is safe, and it belongs there with an explicit list of what it catches: 40001 and 40P01 are worth another attempt, InsufficientFunds and a CHECK violation are the same answer every time. At READ COMMITTED with the lock order above, this design produces neither, so the loop would be dead code today.

          The database is the backstop, not the referee. CHECK (balance >= 0 and balance <> 'NaN') and the foreign keys from ledger to accounts mean a bug in the service cannot leave a negative balance or an orphan row behind, and lock_timeout means a stalled transaction cannot hold a hot account forever. The NaN half is not decoration: postgres orders NaN above every number, so balance >= 0 is true for one and the check that looked like it covered the column did not.

          Money itself is checked before any of this. Numeric(18, 2) rounds on write, and a transfer rounds its debit and its credit separately, so moving 0.125 takes 0.12 from one account and gives 0.13 to the other. Twenty of those mint a cent each and CHECK (balance >= 0) never notices, because what breaks is conservation, not sign. An amount finer than a cent is refused.

          Both claims are automated in tests/test_contention.py, which fails on three tests when the lock is removed and on a fourth when record() stops taking the lock.
